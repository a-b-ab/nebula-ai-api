# 任务中断恢复编码指南

本指南供你自己修改代码；目前只写文档，不修改 Go 源码。目标是在**单实例、旧进程已经停止**的前提下，新进程启动 worker 前，把遗留的 `processing` 任务改为 `failed`，写入中断原因，并把 `finished_at` 设为恢复时刻。

这里的 `failed` 表示“任务没有确认完成”。执行时明确报错、进程中断都会进入 `failed`，但 `error` 字段区分原因。进程异常退出时，无法在退出瞬间写数据库：`processing` 已经持久化，`completed`/`failed` 尚未写入，所以重启后才会看到旧的 `processing`。

## 修改顺序

```text
Repository：批量更新 processing
    ↓
Service：给出中断原因
    ↓
main.go：启动 worker 前调用，失败则停止启动
    ↓
测试：验证状态、错误、结束时间与重复执行
```

请先按每节目标自行编写，再参考代码片段。此次不需要改任务类型，也不需要增加 goroutine 或 Redis Streams。

### 1. Repository：只更新遗留的处理中任务

在 [internal/repository/task.go](../../internal/repository/task.go) 增加方法。使用一条批量 `UPDATE`，用 `WHERE status = processing` 限定范围；返回更新条数，便于启动日志和测试断言。

```go
// FailProcessingTasks 将遗留的处理中任务标记为失败。
func (r *TaskRespository) FailProcessingTasks(reason string) (int64, error) {
    now := time.Now()
    result := r.db.Model(&model.Task{}).
        Where("status = ?", model.TaskStatusProcessing).
        Updates(map[string]interface{}{
            "status":      model.TaskStatusFailed,
            "error":       reason,
            "finished_at": now,
            "updated_at":  now,
        })
    return result.RowsAffected, result.Error
}
```

该文件已有 `time` 和 `model` 导入。`finished_at` 是**恢复时刻**，旧进程实际退出时间无法从当前数据准确得知。`pending`、`completed`、原本的 `failed` 不会匹配条件；再次启动时也不会重复更新已恢复任务。

思考题：为什么不能在 worker 的每次轮询中调用这个方法？答案是正常执行中的任务也处于 `processing`，只有确认旧 worker 已停止、当前 worker 尚未启动时才能批量恢复。

### 2. Service：写清楚失败原因

在 [internal/service/task_service.go](../../internal/service/task_service.go) 为 `TaskService` 增加方法：

```go
const interruptedTaskReason = "上次执行被中断"

func (s *TaskService) RecoverInterruptedTasks() (int64, error) {
    return s.taskRepo.FailProcessingTasks(interruptedTaskReason)
}
```

`Service` 决定业务含义，`Repository` 负责数据库更新。不要调用 `Execute` 或将这些任务重置为 `pending`：当前优化器会向文章正文追加内容，重复执行可能再次追加。

### 3. 启动顺序：恢复成功后才启动 worker

在 [cmd/main.go](../../cmd/main.go) 创建 `taskService` 后、`go taskWorker.Start(...)` 前插入：

```go
taskService := service.NewTaskService(taskRepo, articleRepo, articleOptimizer)

recovered, err := taskService.RecoverInterruptedTasks()
if err != nil {
    log.Fatal("恢复中断任务失败:", err)
}
log.Printf("已将 %d 个上次中断的任务标记为失败", recovered)

// 然后注册路由、启动 worker 和 HTTP 服务。
```

当数据库更新失败时，`log.Fatal` 会阻止新 worker 启动。没有遗留任务时，数量为 0，正常继续。启动前还必须保证没有另一个旧后端进程仍在处理同一数据库中的任务；此实现不支持多实例交叠运行。

## 如何验证

建议在 `internal/repository/task_test.go` 写 PostgreSQL 集成测试，使用**专用且初始没有任务数据的测试库**。测试用事务创建一篇文章和三条任务，事务结束时回滚。由于恢复方法会更新库中**所有** `processing` 任务，不能把日常开发数据库用作测试库。

| 初始状态 | 调用恢复后 | 需要检查 |
| --- | --- | --- |
| `processing` | `failed` | `error` 为“上次执行被中断”，`finished_at` 非空，`started_at` 保留 |
| `pending` | `pending` | `error` 和 `finished_at` 保持原值 |
| `completed` | `completed` | 结果和完成时间保持原值 |
| 第二次调用 | 无新增修改 | `RowsAffected == 0`，原失败原因不被覆盖 |

下面的测试代码可以作为对照。运行前先在专用测试库中创建好 `articles` 和 `tasks` 表，并通过环境变量提供该库的 DSN：

```go
package repository

import (
    "os"
    "testing"
    "time"

    "nebula-ai-api/internal/model"
    "gorm.io/driver/postgres"
    "gorm.io/gorm"
)

func TestFailProcessingTasks(t *testing.T) {
    dsn := os.Getenv("TASK_TEST_DATABASE_DSN")
    if dsn == "" {
        t.Skip("设置 TASK_TEST_DATABASE_DSN 后运行")
    }
    db, err := gorm.Open(postgres.Open(dsn), &gorm.Config{})
    if err != nil {
        t.Fatal(err)
    }
    tx := db.Begin()
    if tx.Error != nil {
        t.Fatal(tx.Error)
    }
    defer tx.Rollback()

    article := model.Article{Title: "测试文章", Content: "正文"}
    if err := tx.Create(&article).Error; err != nil {
        t.Fatal(err)
    }
    startedAt := time.Now().Add(-time.Minute)
    completedAt := time.Now().Add(-time.Second)
    tasks := []model.Task{
        {Type: model.TaskTypeArticleOptimize, Status: model.TaskStatusProcessing, ArticleID: article.ID, StartedAt: &startedAt},
        {Type: model.TaskTypeArticleOptimize, Status: model.TaskStatusPending, ArticleID: article.ID},
        {Type: model.TaskTypeArticleOptimize, Status: model.TaskStatusCompleted, ArticleID: article.ID, FinishedAt: &completedAt},
    }
    for i := range tasks {
        if err := tx.Create(&tasks[i]).Error; err != nil {
            t.Fatal(err)
        }
    }

    repo := NewTaskRepository(tx)
    count, err := repo.FailProcessingTasks("上次执行被中断")
    if err != nil || count != 1 {
        t.Fatalf("首次恢复: count=%d err=%v", count, err)
    }
    recovered, err := repo.GetByID(tasks[0].ID)
    if err != nil {
        t.Fatal(err)
    }
    if recovered.Status != model.TaskStatusFailed || recovered.Error != "上次执行被中断" ||
        recovered.FinishedAt == nil || recovered.StartedAt == nil {
        t.Fatalf("处理中任务恢复结果不正确: %+v", recovered)
    }
    pending, err := repo.GetByID(tasks[1].ID)
    if err != nil || pending.Status != model.TaskStatusPending || pending.FinishedAt != nil {
        t.Fatalf("待处理任务被意外修改: task=%+v err=%v", pending, err)
    }
    completed, err := repo.GetByID(tasks[2].ID)
    if err != nil || completed.Status != model.TaskStatusCompleted || completed.FinishedAt == nil {
        t.Fatalf("已完成任务被意外修改: task=%+v err=%v", completed, err)
    }
    count, err = repo.FailProcessingTasks("上次执行被中断")
    if err != nil || count != 0 {
        t.Fatalf("重复恢复: count=%d err=%v", count, err)
    }
}
```

写完后格式化代码并执行 `go test ./...`；如果没有设置 `TASK_TEST_DATABASE_DSN`，上面的集成测试会跳过，不算完成数据库行为验证。还可以在确认旧进程已退出后，手动准备一条 `processing` 任务并重启后端，检查任务详情和启动日志。

## 这个阶段不解决的问题

若旧进程在写回文章之后、标记 `completed` 之前退出，启动恢复会把任务标成 `failed`，但文章可能已经改变。这里的 `failed` 只表示**未确认完成**，不能据此推断文章完全没被修改；重新发起优化前应检查文章内容。文章写回与任务完成状态的原子提交属于后续阶段。
